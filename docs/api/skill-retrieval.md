# Skill retrieval layer API reference

> Generated by the `doc-generator` skill (Phase 3 Candidate 6 cycle-closure exercise, 2026-04-15). Source: `core/skill/retrieval/`. Target script: `latin`. See the Translation summary at the end for docstrings that still contain non-target or mixed scripts.

## Overview

The retrieval layer is the set of strategies that answer the question *"given a natural-language query, which skills are the most relevant?"* It sits behind `SkillGateway.discover()` and `SkillGateway.search()`, and it is the boundary where user intent gets mapped to skill identifiers.

The layer is organized around one protocol (`BaseRecall`), one data contract (`RecallCandidate`), four concrete strategies, and one fusion coordinator that runs the strategies in parallel and merges their outputs:

```text
                   ┌──────────────────────────────────────────────┐
                   │                MultiRecall                   │
                   │  (fusion coordinator — RRF across strategies)│
                   └──┬──────────────┬──────────────┬─────────────┘
                      │              │              │
            ┌─────────┴────┐  ┌──────┴────────┐  ┌──┴────────────┐  ┌────────────────┐
            │ LocalFile-   │  │ LocalDb-      │  │ LocalBm25-    │  │ RemoteRecall    │
            │   Recall     │  │   Recall      │  │   Recall      │  │  (Skill Market) │
            │ (enumerator) │  │ (vector /     │  │ (lexical /    │  │ (cloud fused    │
            │              │  │  sqlite-vec)  │  │  stdlib BM25) │  │  opaque score)  │
            └──────────────┘  └───────────────┘  └───────────────┘  └────────────────┘
                      │              │                   │                  │
                      └──────────────┴───────────────────┴──────────────────┘
                                                │
                                   list[RecallCandidate]
```

Each strategy returns a `list[RecallCandidate]`. `MultiRecall` merges those lists, stamps per-strategy ranks, applies reciprocal rank fusion (RRF) to candidates that surfaced in both the BM25 and the vector lanes, enforces the local-before-remote tier rule, and returns the final ranked list.

The layer is deliberately additive: new strategies slot in behind `BaseRecall` without changing downstream consumers, and the `RecallCandidate` schema carries optional per-strategy fields so the fusion stage can reason about each strategy's signal without breaking callers that only read `name` and `score`.

## Data contract — `RecallCandidate`

Location: `core/skill/retrieval/schema.py`

`RecallCandidate` is the single shape every strategy returns. Keeping the contract tight here means new strategies (e.g., a future remote-BM25 lane from MS-DES-0010) can add signals without touching downstream consumers.

### Fields

| Field                | Type                          | Default            | Notes |
| :------------------- | :---------------------------- | :----------------- | :---- |
| `name`               | `str`                         | *required*         | Skill name. Stable identifier across strategies — used as the merge key inside `MultiRecall`. |
| `description`        | `str`                         | `""`               | Human-readable description, copied from the `SkillManifest` when available. |
| `source`             | `Literal["local", "remote"]`  | `"local"`          | Tier tag. Drives the local-before-remote sort in `MultiRecall._rerank_candidates()`. |
| `score`              | `float`                       | `0.0`              | *Effective* ranking score. Pre-fusion this is the strategy's own score; post-fusion it holds the RRF-derived fused value. |
| `match_type`         | `str`                         | `""`               | Strategy tag (`"embedding"`, `"local_file"`, `"bm25"`, `"remote"`, etc.). After fusion, becomes `"hybrid"` when the candidate was surfaced by both a lexical and a vector strategy. |
| `skill`              | `Any`                         | `None`             | Full `Skill` object for local candidates; `None` for remote candidates that have not been installed yet. |
| `metadata`           | `dict[str, Any]`              | `{}`               | Loose bag of extra per-strategy fields (e.g., remote-strategy download URL). |

### MS-DES-0004 additions (fusion-stage inputs)

| Field                | Type                          | Default            | Notes |
| :------------------- | :---------------------------- | :----------------- | :---- |
| `bm25_score`         | `float \| None`               | `None`             | Absolute, un-normalized BM25 score assigned by `LocalBm25Recall`. `None` when the candidate did not come out of a lexical index. |
| `vector_score`       | `float \| None`               | `None`             | Cosine similarity from `LocalDbRecall`, expressed as `1.0 - distance` to mirror the existing convention. |
| `bm25_rank`          | `int \| None`                 | `None`             | 1-indexed rank inside `LocalBm25Recall`'s result list. Filled in by `MultiRecall._stamp_rank()` during fusion. |
| `vector_rank`        | `int \| None`                 | `None`             | 1-indexed rank inside `LocalDbRecall`'s result list. Filled in by `_stamp_rank()`. |

All four new fields default to `None`, so callers that only read `name` / `score` behave exactly as they did before MS-DES-0004 shipped.

## Protocol — `BaseRecall`

Location: `core/skill/retrieval/base.py`

Abstract base class for every recall strategy. Enforces a uniform async search interface so `MultiRecall` can treat strategies interchangeably.

### Required members

| Member                                                        | Purpose |
| :------------------------------------------------------------ | :------ |
| `name: str` (property, abstract)                              | Strategy identifier used for logging, rank stamping, and stats. Must be stable — `MultiRecall._stamp_rank()` switches on this string to decide which `RecallCandidate` rank field to populate. |
| `async search(query: str, k: int = 10, **kwargs) -> list[RecallCandidate]` (abstract) | Execute the recall against the given query and return up to `k` results. `**kwargs` is a strategy-specific escape hatch. |
| `is_available() -> bool`                                      | Concrete default. Returns `True` unless overridden. Strategies that can fail (e.g., `RemoteRecall` during a network outage) override to return `False` so the multi-recall skips them. |
| `get_stats() -> dict`                                         | Concrete default. Returns a minimal `{"name": ..., "available": ...}` dict. Strategies override to add size / readiness / catalog fields. |

Docstrings on `BaseRecall` are currently in mixed English + Chinese script (see Translation summary). The method contracts themselves are stable; the docstring language is the only translation-pass concern.

Concrete strategies are free to override the `k` default. Two intentional divergences exist today: `LocalFileRecall.search()` uses `k: int = 0` because it is an enumerator — it always returns every installed skill and ignores the value — and `RemoteRecall.search()` uses `k: int = 5` because each remote round-trip is billed, so the default is deliberately conservative. `MultiRecall` respects the protocol default of `k=10`.

## Concrete strategies

### `LocalFileRecall`

Location: `core/skill/retrieval/local_file_recall.py`

Walks the on-disk `skills/` directory, parses `SKILL.md` files, and returns every installed skill at a flat `score=1.0` with `match_type="local_file"`. **It is an enumerator, not a ranker** — its job is to guarantee that every installed skill is available to downstream consumers, regardless of whether a more sophisticated ranker (vector or BM25) surfaces it.

The cache-invalidation design uses a two-level signature:

- Per-file — SHA-256 over `(mtime, size)` of the skill's `SKILL.md`. Catches content changes.
- Per-directory — rolling signature over the sorted list of top-level entries. Catches add / remove / rename at the directory level.

This is the cheapest possible "is anything different?" check for a filesystem-backed catalog. A full re-scan runs only when either signature changes.

**When to reach for this strategy:** always — it is the safety net. Other strategies rely on it indirectly because `MultiRecall._merge_into_existing()` pulls the full `Skill` object from the local-file hit when a BM25 or vector hit lacks one.

### `LocalDbRecall`

Location: `core/skill/retrieval/local_db_recall.py`

Dense-vector recall over a local SQLite database managed by the `sqlite-vec` extension. Each skill's embedding vector (produced from `name + description` via `SkillManifest.to_embedding_text()`) lives in a vector table; query time is a cosine-similarity top-k.

Key implementation details:

- **Bootstrap assumption.** The class assumes the database has already been initialized by the system startup path. No lazy table creation inside this class — callers must have run the bootstrap first.
- **Embedding client is optional.** Constructor takes `embedding_client=None`. Without a client, the strategy silently returns `[]` from `search()` — used in test harnesses and environments where the embedding API is unavailable.
- **Thread-safe connection.** Uses a module-level threading lock around the sqlite connection because the strategy is consumed from an async event loop that may dispatch queries concurrently.
- **Score is raw cosine similarity** (range `[−1, 1]`, typically `[0, 1]` for normalized embeddings). `MultiRecall._stamp_rank()` populates both `vector_score` (same value) and `vector_rank` (1-indexed position) for the fusion stage.

**When to reach for this strategy:** semantic queries where the user's wording doesn't match a skill's literal name or description. Example: a user asking "help me convert commits to changelog entries" should match the `changelog-writer` skill even though neither "convert" nor "entries" appears in its literal manifest.

### `LocalBm25Recall`

Location: `core/skill/retrieval/local_bm25_recall.py`

Stdlib-only BM25 index over `name + description + body` for every locally-installed skill. Field-weighted by token repetition (`W_NAME=4`, `W_DESC=2`, `W_BODY=1`) with canonical BM25 parameters (`k1=1.2`, `b=0.75`) and an NFKC-normalized Unicode-aware tokenizer. See MS-DES-0004 for the full algorithmic design.

Key implementation details:

- **Pure Python, no third-party deps.** Intentional — the retrospective's "stdlib-first" rule applies here, and keeping the index self-contained means downstream consumers that need the same algorithm (notably `skills/doc-freshness/scripts/doc_importance.py`, which re-derives an equivalent BM25 over docs per MS-DES-0009) can share the approach without pulling in a library. The two implementations are currently independent rather than sharing a module — consolidation would be its own MS-DES.
- **Lazy build on first query.** The index builds on the first call after construction, not at `__init__` time. A query against a just-constructed strategy pays the build cost once; subsequent queries are free.
- **Directory-signature invalidation.** Same rolling-signature mechanism as `LocalFileRecall`. When the skills directory changes, the next query triggers a rebuild.
- **Score is normalized per-query.** The raw BM25 score depends on query length and corpus statistics; it's normalized to `[0, 1]` against the top-scoring document for that query before being returned. `MultiRecall._stamp_rank()` populates `bm25_score` and `bm25_rank`.

**When to reach for this strategy:** exact-name and tool-identifier queries (`"style-checker"`, `"doc-freshness"`, `"MS-DES-0003"`) where lexical precision beats semantic reach. Also the body-text lane — the vector index only sees name + description, so BM25 is the only way to surface a match against prose in the skill body.

### `RemoteRecall`

Location: `core/skill/retrieval/remote_recall.py`

HTTP client for the external `skill_retrieval_api` microservice (the "Skill Market"). Sends a query over `POST /api/v1/search` and returns candidates tagged `source="remote"`, `match_type="remote"`. The remote's score is opaque — the client does not know whether it came from BM25, vectors, or fusion.

Public surface:

| Member                                    | Purpose |
| :---------------------------------------- | :------ |
| `__init__(base_url: str, timeout: float = 10.0)` | Creates an `httpx.Client` with `certifi` TLS and `trust_env=False`. Runs a health check immediately and logs connection state. |
| `classmethod from_config(cls, config)`    | Factory that reads `config.cloud_catalog_url`; returns `None` if unset so callers can no-op the remote lane. |
| `async search(query, k=5, **kwargs)`      | Posts to `/api/v1/search`, maps the response into `RecallCandidate[]`. Returns `[]` on HTTP errors rather than raising — graceful degradation is the point. |
| `is_available() -> bool`                  | Re-probes `/health` on demand. Used by `MultiRecall` to skip the remote lane when the service is down. |
| `embedding_ready: bool` (property)        | Mirrors the remote service's `/health.embedding_ready` field. No BM25-equivalent signal exists today — see MS-DES-0010 open question 5. |
| `close() -> None`                         | Closes the underlying `httpx.Client`. Callers are responsible for invoking this during shutdown. |

Docstrings are mixed English + Chinese throughout (see Translation summary). The method contracts are stable.

**Future work.** MS-DES-0010 proposes extending the fusion stage to treat a dedicated remote-BM25 lane as a third RRF term. That requires a Market-side schema change (one of three proposed shapes, enumerated in the spec). Until then, remote candidates bypass `_apply_fusion()` entirely and participate only via the tier sort.

## `MultiRecall` — fusion coordinator

Location: `core/skill/retrieval/multi_recall.py`

The orchestrator that runs every registered strategy in parallel, merges duplicates, fuses per-strategy signals via RRF, and applies the local-before-remote tier rule. Not a concrete strategy — it does not implement `BaseRecall`; instead it *composes* several `BaseRecall` instances.

### Core pipeline

```text
recall(query, k)
  │
  ├── asyncio.gather(recall.search(query) for recall in strategies)
  │       ↓ per-strategy list[RecallCandidate]
  │
  ├── Step 1 — merge duplicates by `name`, stamping per-strategy rank
  │       ├── _stamp_rank(candidate, strategy_name, rank)
  │       └── _merge_into_existing(existing, incoming)
  │
  ├── Step 2 — fuse per-strategy scores onto `candidate.score`
  │       └── _apply_fusion(candidate)  — RRF math
  │
  ├── Step 3 — sort with tier rule
  │       └── key: (0 if local else 1, -score)
  │
  └── return top-k
```

### Key constants

| Constant        | Value  | Purpose |
| :-------------- | :----- | :------ |
| `RRF_K`         | `60`   | Smoothing constant in the RRF formula `1 / (RRF_K + rank)`. Cormack, Clarke & Büttcher (2009) default. Large enough that rank differences at high rank have diminishing influence; small enough that rank 1 and rank 2 are still meaningfully distinguishable. |

`RRF_K` is declared once, in `core/skill/retrieval/multi_recall.py` — the module that consumes it in `_apply_fusion`. Import it from there. A second copy previously sat in `local_bm25_recall.py` documented as the canonical source but read by nothing; MS-DES-0013 removed it and added a regression guard (`tests/test_skills/retrieval/test_bm25_parity.py`) asserting the single-declaration property.

### Fusion math (two-list form)

For a candidate surfaced in both the BM25 and the vector lane:

```text
RRF(candidate) = 1 / (RRF_K + bm25_rank) + 1 / (RRF_K + vector_rank)
```

For a candidate in only one lane, the missing term is dropped — a BM25-only hit competes on the single-term scale, and the fusion stage sets `match_type="hybrid"` only when both ranks are present.

### Tier rule (invariant)

Local candidates always rank above remote candidates, regardless of fused score. This is a **hard** invariant — the sort key is `(0 if source == "local" else 1, -score)`, so no amount of remote confidence can overtake a local hit. It protects against a noisy Market ranker displacing a good local match, and it aligns with the install-state reality: a local skill is runnable; a remote one requires an install step first.

### Merge semantics for duplicates

`_merge_into_existing()` handles the four cases when the same skill name surfaces in multiple strategies:

- **local over remote** — local wholesale replaces remote. Defensive copy of any existing per-strategy signals from the remote entry.
- **remote into local** — the remote candidate itself is dropped (the local entry wins on the tier rule), but a `metadata["also_available_remote"]` breadcrumb is stashed on the surviving local entry so downstream code can surface "this skill is also installable from the Market" without a second fetch.
- **local + local** — first-seen candidate is retained as base; BM25/vector signals and rank fields from the second are merged in. Description and `Skill` object are promoted if missing.
- **remote + remote** — same-tier merge path; adopts new per-strategy signals when the incoming has them.

### Public methods

| Method                                                   | Purpose |
| :------------------------------------------------------- | :------ |
| `async recall(query, k=10, per_recall_k=None, **kwargs)` | The public entry point. Runs the pipeline above and returns up to `k` candidates. |
| `async search(query, k=10, per_recall_k=None, **kwargs)` | Backward-compatible alias for `recall`. |

The two verbs coexist because `search` is the older surface predating `MultiRecall`'s rename to `recall`; downstream callers that reach `SkillGateway.search()` continue to work without a rename.
